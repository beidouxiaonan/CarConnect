# 0.1.8 SPP 底层恢复依据

## 从反馈确认的部分

0.1.7 实车截图仅显示 C1/C2，随后“SPP 清理超时”和“冷却中”。说明请求返回而 `isSppConnect` 未稳定为 false，尚未发送 CarPlay VF。用户反馈 SPP 空闲时无线能够建立，所以不能把本次故障归因于无线协议整体不可用。

提供的 BC03 1.7.9/1.3.6 文件中，Binder transaction48 的无参 void `SppDisConnect` 转交 HdLinkManager，再交原车 feature。AtPlus 实现为空；AtPound 用其缓存的当前 SPP index 发送 VH。截图不提供活跃 feature 类型或 native 回执，因此“本车一定走空方法”仍是推断，不能作为已实测事实。

## 新增的已核对 native 路径

输入 gocsdk SHA256 固定为 `3e8f5687b69623087145177358c2104aeae50f2eb943db8711af983e395ced60`。命令字符串数组中的 VF/VG/VH 与处理函数数组的相同索引对应；VH 处理函数为 Thumb `0xa0868`。参数首字节为 0 时，分支以 index0 开始、循环至8，每次调用 `disconnect_spp`；非空参数走指定 index。命令匹配返回参数起点，UART 帧处理以 CR/LF 结束并写入 NUL。

`verify_native.py` 在构建前验证文件哈希、相邻命令映射与无参数分支字节。公开文件只含自编检查器、摘要和说明，没有 OEM 二进制或原反编译文件。静态分析确认接口语义，不替代实际模块执行结果。

本版只在已核对 BC03 1.7.9/1.3.6 APK 与上述 daemon 的组合中使用无索引 `AT#VH\r\n`。沿用 VF 使用的可写 `/dev/goc_serial`，要求真实路径是 `/dev/pts/数字`，只写不读 UART，避免抢走原服务回执。接口不枚举进程，不杀其他应用，不调用模块电源/reset，也不猜当前 SPP index。

## 时序与边界

启动仅查询，清理只在真实连接前执行。先请求原 Binder，5 秒未释放后最多写一次 native 清理，再等待12秒；观察稳定300ms才继续。总状态等待上限约17.3秒，IPC或驱动调用本身耗时不计为可保证的实时期限。异步写入不能证明执行成功，不改缓存、不伪造未连接状态。

使用原 `oemSppCleanup` 保存开关，默认关闭。自己活动通道受保护。未完成的旧 VF 在45秒内禁止新清理；原请求已发出时不能撤销，取消只停止后续动作。清理后再次验证已记住手机、原车当前手机与模块MAC；空闲状态变回占用时停止，不抢接。

普通 APK 无法承诺“一次彻底解决”。后台自动重连、原服务缓存不更新、系统拒绝串口、不同 daemon 或模块行为都可能仍失败。需要看新 C4/C5 和实际连接结果；没有新包车机回执前只称兼容测试。

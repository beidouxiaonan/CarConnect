# CarConnect 0.1.7 beta · BC03 1.7.2 SPP 清理与接入测试

以已发布的 **CarConnect 0.1.6 beta · BC03 1.7.2 SPP 接入测试** APK 为基线，合入 OEM SPP 自动清理开关。显示版本 `Carplay-connect-0.1.7-beta-BC03-172-SPP-cleanup-test`，versionCode47。原有 S1～S6 有限数据验证、音视频优化、手机记忆及 VF 冷却保留。

## 操作

1. 覆盖安装 `CarConnect-0.1.7-beta-BC03-1.7.2-SPP-cleanup-test.apk`，无需卸载旧包；手机、热点、音量与帧率设置保留。
2. 打开“无线连接、画面与音量设置”，保持“使用原车蓝牙连接 iPhone”开启，再开启 **启动及连接前自动清理原车 SPP**。新开关默认关闭且保存；如果此前已在 OEM 清理包中保存开启，则沿用该记录。
3. 先让原车蓝牙连接已配对 iPhone，开启车机热点，手机保持 Wi-Fi / 蓝牙开启，再等待 CarConnect 自动无线连接。
4. 失败时复制“连接诊断”，包含 C1～C3、S1～S6、协议收发字节数及最终 iAP2 错误。冷却时等待提示倒计时结束，不连续反复尝试。

## 清理与探测的顺序

启动检查在后台按进程执行一次；每次原车连接前再次检查。CarConnect 自己的活动通道及正在建立连接时受保护，页面重建不会清理当前会话。

先核对服务、手机记录与 VF 冷却。VF 请求仍在45秒窗口内时停止，**暂不查询/断开 SPP**，避免打断前一条未完成请求。之后没有占用就继续；有占用且开关关闭时拒绝抢占；开关开启时调用原车 `SppDisConnect()`，最多等待5秒且未连接状态连续稳定300ms才允许继续。

清理请求也至少间隔45秒。清理失败、取消、手机/模块地址变化或再次占用时不发 VF。确认空闲后进入原有 VF → 15秒 SPP 状态等待 → 仅已核对1.7.2在缺失状态时限时接入 → 8秒无回包关闭本应用客户端 → 原有 iAP2 握手验证流程。不将断开请求返回、首批字节或状态缺失当作 CarPlay 成功。

| 诊断 | 含义 |
| --- | --- |
| C1 未发现占用 | 不发送断开请求 |
| C1 检测到占用 | 按已开启的开关准备请求释放 |
| C2 请求返回 | 只是调用返回，尚未确认释放 |
| C3 稳定300ms | 确认服务上报未连接后继续 |
| 清理超时/冷却 | 本轮停止，不发送 VF |
| VF 冷却，暂不清理 | 等待上次请求窗口结束 |
| S1 / S2 | 本地 socket / VF 写入，不能证明无线已连接 |
| S3 未上报 SPP | 仅1.7.2进行一次有限数据验证 |
| S4 / S5 | 地址登记并交给原有 iAP2，尚非 CarPlay 成功 |
| S6 8秒无数据 | 关闭本应用客户端，等待冷却 |
| S6 首批协议数据 | 继续查看原有 iAP2 验证结果 |

## 范围

仅核对 BC03 1.7.2 / 1.7.9 / 1.3.6 和指定 gocsdk SHA256。开启清理可能中断原车服务当前管理的其他 SPP 投屏/数据连接。普通 APK 无法枚举或强杀所有后台 SPP 实例，不清理未知进程、不关闭整个蓝牙、不删除配对，也不请求断开 HFP/A2DP。

原服务断开入口为空、状态不更新、模块不支持或其他应用立即回连时仍会失败。最低 API17、ARMv7、纯V1、相同测试签名可覆盖安装。47项本地测试与静态检查通过，**尚无实车验证**；既有 K2001N 有线重启问题未解决，保持无线模式。
